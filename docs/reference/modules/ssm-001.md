# `ssm-001` — ssm:StartSession

|  |  |
|---|---|
| ID | `ssm-001` |
| Category | existing-passrole |
| Services | iam, ssm |
| Author | Seth Art |
| Aliases | `ssm-startsession`, `exploit/ssm_startsession` |
| pathfinding.cloud | https://pathfinding.cloud/paths/ssm-001 |

Use ssm:StartSession to remotely access a running EC2 instance via AWS Systems Manager Session Manager, then execute the selected payload using the instance role's permissions. Payloads can exfiltrate credentials, create IAM backdoors, or establish a reverse shell. The attack provides SSH-like access through the AWS API without requiring network connectivity to the instance or open SSH ports.

## Required permissions

- `ssm:StartSession` — Must be allowed on both the target EC2 instance AND the SSM-SessionManagerRunShell document (arn:aws:ssm:*:*:document/SSM-SessionManagerRunShell)

## Additional permissions

- `ec2:DescribeInstances` — Helpful for discovering EC2 instances with privileged instance profiles
- `ssm:DescribeInstanceInformation` — Helpful for identifying SSM-enabled instances and verifying agent online status
- `ssm:TerminateSession` — Allows ending the SSM session cleanly after exploitation
- `sts:GetCallerIdentity` — Useful for verifying stolen credentials after exfiltration

## Prerequisites

**Admin:**
- A running EC2 instance must have a privileged IAM role attached via instance profile
- The instance must have the SSM agent installed and running (Amazon Linux 2, Amazon Linux 2023, and Ubuntu 18.04+ include it by default)
- The instance role must have the AmazonSSMManagedInstanceCore policy (or equivalent) to enable SSM connectivity
- The operator must have ssm:StartSession permission on both the target instance and the SSM-SessionManagerRunShell document
- The AWS Systems Manager Session Manager plugin must be installed locally

**Lateral:**
- A running EC2 instance with a privileged IAM role attached via instance profile
- The instance must have the SSM agent installed and running
- The operator must have ssm:StartSession permission on the target instance

## Options

| Name | Required | Default | Description |
|------|----------|---------|-------------|
| `INSTANCE_ID` | yes | — | Target EC2 instance ID (must have SSM agent running and a privileged IAM role attached via instance profile) |
| `PAYLOAD` | yes | — | Payload to execute on the instance (run 'payloads list' to see available options) |
| `REGION` | no | `us-east-1` | AWS region where the target instance runs |

## Compatible payloads

- `backdoor/attach-policy` — Attach a policy to an IAM user or role using the instance role's IAM permissions
- `backdoor/create-access-key` — Create access keys for an IAM user using the instance role's IAM permissions
- `backdoor/create-role` — Create an IAM role with administrator privileges using the instance role's IAM permissions
- `backdoor/create-user` — Create an IAM user with administrator privileges using the instance role's IAM permissions
- `backdoor/update-role-trust` — Append a trust policy statement to an IAM role using the instance role's IAM permissions
- `exfil/https` — Exfiltrate instance role credentials to an attacker-controlled HTTPS endpoint via SSM command
- `exfil/s3` — Exfiltrate instance role credentials to an attacker-controlled S3 bucket via SSM command
- `revshell/tls` — Establish a TLS-encrypted reverse shell via SSM command
- `shell/interactive` — Open a live interactive shell via the SSM session (no reverse connection required)
