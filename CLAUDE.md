This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Related Projects

Pathrunner is one of three projects sharing the `{service}-{number}` identifier convention for AWS privilege escalation paths:

Layout: all three projects live side-by-side under a shared `pathfinding/` parent, so from within pathrunner the siblings are `../pathfinding.cloud/` and `../pathfinding-labs/`.

- **pathfinding.cloud** (`../pathfinding.cloud/`) — Source of truth. YAML path definitions in `data/paths/{service}/{service}-{number}.yaml` with permissions, prerequisites, exploitation steps.
- **pathfinding-labs** (`../pathfinding-labs/`) — Terraform lab environments in `modules/scenarios/`, each with `scenario.yaml`, `demo_attack.sh`, `cleanup_attack.sh`, and Terraform modules.
- **pathrunner** (this repo) — Automates exploitation. See `pkg/exploits/register.go` (auto-generated) for the current list of registered modules; new modules appear there automatically after `go generate ./pkg/exploits/`.

```
pathfinding.cloud (YAML) → pathfinding-labs (Terraform) → pathrunner (execution)
  lambda-001.yaml           scenario.yaml / demo_attack.sh   pkg/exploits/lambda_passrole/
```

The `{service}-{number}` ID links path definition → deployable lab → automated exploit module. Pathrunner's `PathInfo` struct mirrors the subset of pathfinding.cloud fields useful at runtime.

## Build and Development Commands

```bash
make build                                       # Regenerates pkg/exploits/register.go then builds with version info
make generate                                    # Regenerate pkg/exploits/register.go only
make dev                                         # Dev mode with version info (no regenerate)
make test                                        # Run all tests
make clean                                       # Remove built binary
go build -o pathrunner cmd/pathrunner/main.go     # Build (no version injection, no regenerate)
go run cmd/pathrunner/main.go                     # Dev mode (no version injection)
./pathrunner [command] [subcommand] [flags]       # CLI mode
./pathrunner                                      # REPL mode
go test ./tests/unit/                             # Unit tests
go test ./tests/integration/                      # Integration tests
go test ./tests/...                               # All tests
go test -v ./tests/... -run TestName              # Specific test
```

`make build` runs `go generate ./pkg/exploits/` before compiling, so newly added exploit module directories are picked up automatically. `scripts/test-module.sh` provides a heavier smoke-test harness for individual modules against deployed labs.

## Architecture Overview

Modular AWS post-exploitation framework with dual CLI/REPL interfaces sharing the same business logic.

### Packages

- **pkg/core/** — REPL shell (`repl/`), identity management (`identity.go`), session persistence (`session.go`), adapter pattern (`repl_adapters.go`). The REPL handles command parsing, tab completion, and dispatching.
- **pkg/cli/** — Cobra CLI wrapper mapping 1:1 with REPL commands via adapters.
- **pkg/modules/** — Module system: `Module` interface, `BaseModule` embeddable struct, `PathInfo` metadata, global registry with alias support and search/filter. Optional interfaces: `PayloadCompatible`, `Discoverable`.
- **pkg/payloads/** — Centralized payload registry: `Payload` interface, tag-based filtering (`TagFilter`), service subdirectories (`ec2/`, `lambda/`, `glue/`). Optional interfaces: `Verifiable`, `SideEffectReporter`.
- **pkg/exploits/** — Exploit modules, each embedding `BaseModule` and living in its own subdirectory. `register.go` is auto-generated by `scripts/gen_register.go` (invoked via `//go:generate` in `gen.go`); it fans out blank imports for every module directory so `init()` registration fires. `shared/` holds helpers reused across exploit modules.
- **pkg/discovery/** — Reusable AWS enumeration: IAM roles by trust policy, instance profiles, DynamoDB streams. Used by modules implementing `Discoverable`.
- **pkg/attacker/** — Attacker-side infrastructure: unified TLS listener for reverse shells + HTTPS credential collection (`listener.go`, `shell_handler.go`, `creds_handler.go`, `certs.go`), attacker EC2 box deployment (`deploy_ec2.go`), exfil S3 bucket deployment (`deploy_bucket.go`, `s3.go`), shared deploy state (`deploy_state.go`), public IP detection (`ip.go`), event logging (`listener_events.go`, `listener_state.go`).
- **pkg/pmapper/** — PMapper graph integration: import saved PMapper graphs (`import.go`, `store.go`), map PMapper edges to pathrunner module IDs (`mapping.go`), query privilege paths and analyze self-escalation (`query.go`, `selfescalation.go`).
- **pkg/status/** — Module status tracking (tested-against lab, working/broken flags) for the `modules status` / `modules mark-*` commands.
- **pkg/ui/** — Terminal UI primitives (Bubbletea/lipgloss): path view rendering, panels, tables, gradients, prompt styling.
- **pkg/aws/** — AWS SDK helpers shared across packages.
- **pkg/version/** — Build metadata (linker-injected `Version`, `GitCommit`, `BuildDate`).
- **pkg/utils/** — Credential extraction from env vars, JSON, Python dicts.
- **pkg/config/** — Application configuration.

### Key Design Patterns

**Dual Interface**: REPL and CLI share command handlers via `ExecuteCommand()`. CLI uses adapter pattern to bridge concrete types with REPL interfaces.

**Workspace-Scoped Identities**: Each workspace maintains isolated AWS identities. `loadSessionState()` replaces (not merges) identities on switch. Workspaces persist as JSON in `~/.pathrunner/sessions/`.

**Identity Management**: Supports AWS profiles, env vars, static keys, credential extraction. Auto-refreshes SSO via `RefreshConfig()`. Auto-imports credentials from exploit output (structured `--- PATHFINDER_IDENTITY_DATA ---` markers or general extraction via `utils.ExtractCredentialsFromText()`). AWS CLI passthrough injects current identity as env vars.

**Payload Registry**: Payloads are decoupled from modules and self-register via `init()`. The registry is **modular and service-scoped**: each payload lives under `pkg/payloads/{service}/` (`ec2/`, `lambda/`, `glue/`), tags itself with `TagService{Name}`, `TagLanguage{...}`, `TagTechnique{...}`, and `TagTransport{...}`, and modules query the registry by tags at runtime (`GetPayloadsByTags`, `GetPayloadForService`). The same logical action (e.g., `backdoor/attach-policy`) can exist independently under each service — the composite key `(service, name)` disambiguates them. Each payload implements `GenerateCode(options)` (Python for Lambda/Glue, bash for EC2) and `ProcessResult(result)`. Modules declare compatibility via `PayloadCompatible` interface (`GetCompatibleTags()`, `GetPayloadContext()`), which lets a single module surface all payloads registered for its service without hardcoding them.

**Optional Payload Interfaces** (in `pkg/payloads/interface.go`):
- `Verifiable`: For event-triggered modules — verify payload effect (e.g., check if policy attached). Used in trigger-and-verify retry loops.
- `SideEffectReporter`: For payloads modifying existing resources — reports modifications for cleanup tracking. Modules call `ReportSideEffects()` after execution and set `ModuleID`/`Region` on returned resources.

**Optional Module Interfaces** (in `pkg/modules/interface.go`):
- `Discoverable`: Auto-discover option values via AWS API. Methods: `DiscoverableOptions()`, `Discover()`. Uses `pkg/discovery/` utilities. Auto-triggered at exploit time if required options are missing.

**Lambda Environment Variables**: Event-triggered payloads read parameters from `os.environ`; modules set them via `CreateFunctionInput.Environment` — never hardcode values in Python source.

**Module Output for Auto-Import**: Modules outputting credentials should include structured data between `--- PATHFINDER_IDENTITY_DATA ---` / `--- END_PATHFINDER_IDENTITY_DATA ---` markers with NAME, TYPE, ACCESS_KEY_ID, SECRET_ACCESS_KEY, SESSION_TOKEN, REGION, EXPIRES_AT, AUTO_SWITCH fields. See `/create-module` skill's module-patterns.md for the full template.

**Registration**: Both modules and payloads self-register via `init()`. Modules: `modules.Register(id, constructor)` with pathfinding.cloud ID as primary key; aliases auto-registered from `PathInfo.Aliases`. Payloads: `payloads.Register()`. Exploit modules are wired in via `pkg/exploits/register.go`, which is generated by `scripts/gen_register.go` (`go generate ./pkg/exploits/`, run automatically by `make build`); `cmd/pathrunner/main.go` does one blank import of `pkg/exploits`. Payload sub-packages are still imported explicitly in `main.go` (`pkg/payloads/ec2`, `pkg/payloads/lambda`, `pkg/payloads/glue`).

**Command Aliases**: `identities` -> `identity`, `workspaces` -> `workspace`, `quit` -> `exit`. All have full tab completion.

### Attacker Infrastructure

`pkg/attacker/` implements the attacker-controlled side of trigger-and-callback exploits: a single `UnifiedListener` handles both an HTTPS `/collect` endpoint for exfiltrated credentials and a TLS reverse-shell listener on separate ports (defaults 8443 / 4444). Callbacks (`OnCredReceived`, `OnShellConnected`, `OnEvent`) wire it into the REPL — collected creds auto-import as identities, shells surface via `sessions list/interact/kill`. Deployment helpers can spin up an EC2 attacker box (so the listener can run remotely, reachable from AWS-side payloads) and/or an exfil S3 bucket, with state persisted per-workspace.

The listener is deploy-agnostic: it can run locally on the operator's machine (payloads dial back over the operator's public IP) OR on the attacker EC2 box provisioned by `attacker infra ec2 create` (payloads dial the EC2 public IP). The `listener` command started via SSH on the attacker box uses the same code as the local listener — the "remote listener" is just the same binary, same `UnifiedListener`, running on the deployed EC2 host.

**Auto-injection of payload options**: When `attacker listener start` runs and resolves a public IP, it populates the REPL's `HTTPS_URL`, `LISTENER_IP`, and `LISTENER_PORT` options if they aren't already set (see `injectListenerOptions` in `pkg/core/repl/attacker_listener.go`). This means payloads like `revshell/tls`, `exfil/https`, and `exfil/s3` don't require the operator to manually copy the listener's IP into module options — starting the listener wires them up.

REPL surface:
- `attacker identity show|add|remove|validate` — attacker AWS identity used by deploy commands (separate from the victim identity). Persisted globally to `~/.pathrunner/attacker_identity.json`, shared across workspaces (like deploy state and listener state). Legacy aliases `attacker set/show/clear/validate` still work.
- `attacker listener start|stop|status|log` — the unified listener (local or on the deployed attacker EC2 box)
- `attacker infra ec2 create|update|status|destroy` — deploy/update/destroy the attacker EC2 box
- `attacker infra bucket create|status|destroy` — deploy the exfil S3 bucket used by `exfil/s3` payloads
- `sessions list|interact|kill` — reverse-shell session manager (backed by `UnifiedListener.SessionManager`)
- Top-level `listener` command is an alias for `attacker listener`.

**Payloads that depend on attacker infra**:
- `revshell/tls` requires `LISTENER_IP` (+ optional `LISTENER_PORT`, default `4444`) — auto-injected by `attacker listener start`
- `exfil/https` requires `HTTPS_URL` — auto-injected as `https://<PublicIP>:<HTTPSPort>/collect`
- `exfil/s3` requires `EXFIL_BUCKET` — auto-populated from `attacker.GetExfilBucket()` once `attacker infra bucket create` has provisioned one (see the auto-populate logic in `pkg/core/repl/module.go`; same path also defaults `TARGET_ARN` to the current identity's ARN)

### PMapper Integration

`pkg/pmapper/` consumes graphs produced by the external PMapper tool (`pmapper graph create` → JSON), maps PMapper's `edge_type` labels to pathrunner module IDs, and produces per-identity privilege-escalation reports. The `pmapper import <file>` command loads a graph into `~/.pathrunner/graphs/`; `pmapper analyze [identity]` runs privilege queries for the current or named identity; `pmapper status` reports what's loaded. Analyzed steps include suggested pathrunner commands to actually execute the path.

### AWS Integration

**Credential Refresh**: Profile names persisted, AWS configs rebuilt on-demand via `RefreshConfig()`.

**Resource Tracking**: Modules must call `tracker.TrackResource()` for created resources and check for `SideEffectReporter` on payloads to track modifications. Cleanup is region-aware, interactive via `survey/v2`, with permission error guidance.

**Cleanup Report**: `workspace report` generates handoff report with manual AWS CLI cleanup commands. Supports `--module <id>` filtering.

**Timeouts**: 30-second timeouts for AWS operations (SSO credential resolution).

## Testing Strategy

**IMPORTANT**: All new commands and features MUST have both unit and integration tests.

### Test Structure

```
tests/
├── unit/          # Business logic in isolation — config, identity, session, REPL commands,
│                  # payloads, pathinfo, discovery, attacker (deploy + listener), pmapper,
│                  # status, listener state, cleanup, context, sessions
└── integration/   # End-to-end command workflows — identity, workspace, commands, pathinfo,
                   # cleanup, report, discovery, attacker (deploy + listener), pmapper,
                   # status, sessions, IAM modules, glue_passrole_job
```

Common test setup uses `setupTest(t)` in `tests/integration/setup_test.go` which creates a temp HOME, initializes managers and adapters, and returns a cleanup function. Heavier per-module smoke testing lives in `scripts/test-module.sh`.

### Requirements

- Unit tests: test initialization, core logic, validation, error handling
- Integration tests: test successful execution, validation errors, error scenarios, aliases
- State-related features: test workspace isolation (setup in workspace A, switch to B, verify clean, switch back, verify restored)
- All CLI/REPL commands need end-to-end tests through `r.ExecuteCommand()`

## Session Data Storage

Workspaces persist as JSON in `~/.pathrunner/sessions/`: identities map (aws.Config rebuilt on load), current identity, command log, created resources, current module, options. The attacker identity is stored globally at `~/.pathrunner/attacker_identity.json` (shared across all workspaces), alongside deploy state (`deploy.json`) and listener state (`listener.json`).

## Common Gotchas

**AWS Config Persistence**: `aws.Config` has `json:"-"` tag. Must call `RefreshConfig()` when loading from JSON.

**Module Execution Signature**: Modules embed `BaseModule`, implement `Options()` and `Execute(identity, options, tracker)`. Override `PayloadOptions()` and `ListPayloads()` if supporting payloads.

**Payload Code Generation**: Lambda payloads generate Python, EC2 payloads generate bash. Use `'''` for multiline JSON in Python, not backticks. Pass runtime params via `os.environ.get()`, not string concatenation.

**Import Cycles**: Module interfaces in `pkg/modules/` stay separate from core. Payloads depend on `pkg/modules/` for `Option` type but never import core or exploits.

**Workspace Isolation**: Features storing state must respect workspace boundaries via `loadSessionState()` / `saveCurrentState()`.

**Command Naming**: Singular form (e.g., `identity`, `workspace`), aliases handle plurals.

**Error Types**: `NewCommandNotFoundError()`, `NewInvalidArgumentsError()`, `NewIdentityRequiredError()`, `NewExecutionError()`.

**Subcommand Help**: Every command/subcommand MUST support trailing `help`. Help checks go at top of handler, before validation.

## Development Workflow

### Adding a New Command / Subcommand / Option

The canonical checklist — CLI and REPL share handlers, so every entry point needs to be updated in both interfaces plus completion. Common mistakes are omitting the alias completers, forgetting the `help` subcommand handler, or updating one interface but not the other.

- [ ] Handler in `pkg/core/repl/*.go`
- [ ] Registered in `pkg/core/repl/commands.go` `getCommands()` map
- [ ] Cobra wrapper in `pkg/cli/commands.go` (wired in `pkg/cli/cli.go`)
- [ ] `show*Help()` function + `help` argument check at the top of the handler (also for each subcommand)
- [ ] Tab completion in `pkg/core/repl/completion.go`, including alias completers
- [ ] Unit tests in `tests/unit/` and integration tests in `tests/integration/`
- [ ] Manually verify tab completion in a running REPL

### Adding a New Module or Payload

Use the `/create-module` skill, which has complete step-by-step workflows, Go templates, and a verification checklist in its supporting files (module-patterns.md, payload-patterns.md, checklist.md).

Exploit modules are picked up automatically: create the module directory under `pkg/exploits/`, and `make build` (or `go generate ./pkg/exploits/`) regenerates `pkg/exploits/register.go` with the new blank import. No manual edit to `cmd/pathrunner/main.go` is needed. Payload sub-packages, if you introduce a new service directory, still need a blank import added in `main.go`.

## Code Style

- **Error Messages**: Lowercase, no trailing punctuation
- **User Messages**: Capitalized sentences, proper punctuation
- **Variable Naming**: Descriptive (e.g., `identityManager` not `im`)
- **Comments**: Exported functions must have godoc comments
- **Test Names**: `TestFeatureSpecificBehavior` format
